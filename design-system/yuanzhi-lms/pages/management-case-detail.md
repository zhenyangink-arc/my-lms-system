# Management case detail

- Route: `/admin/accounts/[profileId]`, `/admin/documents/[studentId]`, `/admin/visa/[studentId]`; tenant variants at `/admin/tenants/[tenantId]` and `/admin/tenants/history` under either tenant-scoped or platform-scoped management bases.
- Audience: Management
- Archetype: Detail / inspector; `/admin/tenants/history` is Audit / history.
- Primary job: Identify the current student, account, or tenant; understand its status and related records; then perform only the contextual actions allowed by the viewer's scope.
- Primary action: Context-dependent review or lifecycle action. Back navigation remains secondary, and destructive actions remain last, visually separated, and confirmation-gated.
- Information hierarchy: Shared account/document/visa composition is identity and context header → concise status metrics → grouped case sections and immutable records → contextual actions → history or destructive zone. A valid case with no child records uses a labeled empty state; a missing or inaccessible subject must use not-found or permission handling instead of the empty state.
- Layout and density: Desktop Management standard/compact density. Use the shared `ManagementPage` shell, stable opaque surfaces, full-width tables where comparison matters, and horizontal overflow only for genuinely wide structured data. Keep one page H1 in the shared header; section titles start at H2.
- Special components: `ManagementPage`, `ManagementMetricStrip`, summary/detail tables, labeled empty and error notices, expandable secondary forms, audit dialogs/tables, and confirmation dialogs for destructive actions.
- Allowed deviations: Account detail may use several single-record comparison tables and place its audit history in a dialog. Document review may repeat one H2 section per university application and place the create-item form after existing applications. Visa detail may combine case settings, arrival facts, and task review in one inspector surface before its destructive zone. Tenant detail replaces student-case sections with institution membership followed by lifecycle actions. Tenant history uses the Audit composition: read-only notice/context → recoverable-tenant index → filtered immutable lifecycle and membership records; it must not expose edit or delete controls on audit entries.
- Accessibility risks: Duplicate identity headings, skipped H2 levels, unlabeled wide tables, focus indicators lost on links or native disclosure summaries, decorative icons announced as content, color-only status, and destructive actions presented without confirmation. Nested controls must preserve accessible names, announced expanded/pressed states, and visible keyboard focus.
- Acceptance criteria: Exactly one page H1; identity precedes sections and actions/history; all interactive controls are keyboard reachable with visible focus; decorative icons are hidden and icon-only controls are named; loading, empty, error, permission, and not-found outcomes are distinguishable; no raw color values or removed `--app-*` tokens appear in page components; destructive actions require confirmation; audit records are immutable and filterable when filters are present; layouts remain operable at supported desktop widths and zoom levels.
