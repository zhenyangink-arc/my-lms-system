# Korean practice runner

- Route / pattern: `/[space]/apps/korean/practice/course/[courseKey]/[chapterSlug]`; `/[space]/apps/korean/practice/skills/[skill]`; `/[space]/apps/korean/practice/skills/vocabulary`; `/[space]/apps/korean/training/[skill]/[courseSlug]/[lessonSlug]/[chapterSlug]`.
- Audience: Student; platform tenant managers may bypass the learning sequence for inspection.
- Archetype: Practice runner / focused exercise.
- Primary job: Complete one bounded Korean review or skill-training activity with clear progress, feedback, and a reliable return path.
- Primary action: In the course-chapter variant, complete the current knowledge interaction and continue to the chapter test; in the skills variant, answer every question and submit the practice result.
- Information hierarchy: Student shell H1 → runner H2 and context → progress/status → focused learning or question content → completion/next action. Supporting summaries and lesson groups use H3 only below their owning H2.
- Layout and density: Comfortable student density. The course-chapter variant uses a wide learning workbench with a sticky progress/actions rail; the skills catalog uses a bounded course/lesson directory; the selected skills exercise uses a reading/progress rail beside the active question. Exercise, reading, answer, and feedback surfaces are opaque; only shell chrome or modal overlays may visually separate layers.
- Special components: `KnowledgeResearchWorkbench`, `KnowledgeInteractionLab`, `ToolboxPracticeRunner`, `ToolboxStudyTimer`, native disclosure controls, semantic progress indicators, speech playback, learning-sequence locks, and route loading/error boundaries.
- Loading / empty / error / permission states: Route-family loading files provide loading feedback. Unknown course, lesson, chapter, or skill identifiers use `notFound()`. Query failures render a retry-oriented unavailable state rather than a false empty or 404 state. Empty course, lesson, chapter, exercise, and question collections have explicit copy. Locked course-chapter and skill-training routes explain the prerequisite and link back to the applicable catalog. `requireActiveUser()` redirects unauthenticated and inactive accounts; the Student shell remains responsible for application membership/permission admission.
- Allowed deviations: The course-chapter runner may open its four-part interaction lab in a modal work surface after prerequisite cases are explored. Skills routes may first render a course/lesson/chapter catalog and then use the same page implementation for the selected training route. These are two composition variants in one specification because they share the same audience, runner archetype, state model, semantic-token policy, heading contract, and exit behavior; separate documents would duplicate those governing rules without introducing an independent page contract.
- Accessibility risks: Shell/content heading duplication, selected modes or correctness conveyed only by color, decorative icons announced repeatedly, speech controls without usable names, focus loss when the interaction dialog closes, hidden focus at sticky rails, and locked or failed data presented as missing content.
- Keyboard and focus risks: Every link, disclosure, mode, case, audio, previous/next, submit, reset, and dialog control must be keyboard reachable with a visible focus indicator. Mode and case selection expose selected/pressed state. Opening the interaction dialog moves focus inside it; Escape and the named close control dismiss it and return focus to the launcher.
- Color and feedback contract: Runtime UI uses semantic or approved component tokens only—no raw hex/RGB/RGBA values and no `--app-*` namespace. Correct, incorrect, completed, locked, selected, loading, and failed states pair color with visible text, an icon, a border/shape change, or native control state.
- Desktop width and zoom risks: At 1024 / 1280 / 1440 / 1920px and 100–200% zoom, the sticky rail must not cover focused controls, question actions must wrap without horizontal scrolling, modal content must remain scrollable, and long Korean/Chinese labels must remain available.
- Acceptance criteria: Exactly one shell H1 is followed by runner H2 and sequential descendants; core content is opaque; all runner controls have visible keyboard focus and icon-only controls have accessible names; decorative icons are hidden; dialog focus returns to its launcher; progress and correctness are not color-only; loading, empty, error, missing, and permission/lock states remain distinct with recovery; no raw palette values or legacy app tokens occur in the audited runner files.
