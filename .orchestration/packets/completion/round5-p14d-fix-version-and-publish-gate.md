# Packet: Round5/Packet14d — 修复迁移版本号排序 + 诊断007的"题库已发布"阻断

## 背景
Packet14c已新增引导性平台负责人迁移，但暴露两个问题：
1. 命名`202608190006005000_bootstrap_platform_owner_audit_subject.sql`排序错误
   （实测排在006之前，不是006/007之间），根因是数字字符ASCII小于下划线，
   导致更长的纯数字前缀整体排序更靠前。
2. 即便负责人问题解决，`202608190007_seed_korean_chapter_one_pilot_papers.sql`
   仍会因"韩国语一级第一章正式题库不存在或尚未发布"而阻断——16章教材当前均为
   `draft`。此前Round1处理004（`202608190004_fix_listening_backfill_trigger_order.sql`）
   时的先例是：004的`published`筛选条件本身是逻辑缺陷（草稿内容本应同样可用作
   听力素材来源，用户已授权直接放宽该条件）。这次要判断007的"题库须已发布"要求
   是否属于同类可放宽的过度限制，还是这次真的必须要有已发布内容（例如007生成的
   是要给学生使用的正式试卷，依赖已发布题库有正当理由）。**不允许**用"强制把16章
   标记为published"来绕过（此前Packet14b/2c已明确否决这种桥接迁移，会错误地把
   仍处于editorial_review等pending状态的教材标记为正式发布）。

## 目标
1. 先修正迁移版本号，确保真实介于006和007之间（可考虑改用007自身之前更早、
   有间隙的位置，或改用其他Supabase支持的排序方式；需要先验证清楚Supabase CLI
   实际按什么规则排序迁移文件名，不要再次凭猜测命名）。
2. 诊断007"题库须已发布"检查的具体查询条件（表、字段、状态值），判断：
   a) 该限制是否类似004一样是过度限制（草稿题库内容其实完整可用，只是没点发布），
      如果是，参照004先例，说明是否需要同样的"放宽筛选条件"处理，并给出具体位置。
   b) 如果确实需要真正"已发布"语义（比如是要生成学生能看到的正式试卷，理应只用
      审核通过内容），说明这种情况下唯一干净的解法可能是：本迁移专门为这几个
      "试运行/种子"用途创建一个独立的、不影响真实16章教材状态的最小化已发布内容
      快照（而不是把真实教材整体标记published），评估是否可行、复杂度如何。
3. 提出至少两个方案，明确各自是否需要修改007/008/014/023/200002本身（如需要，
   按此前先例，说明这需要用户像004一样单独授权，不要自行动手改）；如果方案不需要
   改这些历史文件（比如只在新引导迁移里额外补一份最小化种子内容），可以直接实现。
4. 实现你判断可行且不需要改历史文件的方案，让`npx supabase db reset --local`
   完整跑通到`202608200008`，迁移账本正确登记。

## 非目标
- 不自行修改007/008/014/023/200002等任何历史迁移文件（如判断必须改，先在报告中
  说明原因和两种以上方案，不要动手，交由下一轮明确授权）。
- 不在正式管理界面或真实16章教材数据上做任何发布状态变更。

## 验收标准
1. 明确回答Supabase迁移文件排序的真实规则，并给出验证依据。
2. 新引导迁移（可以是修正版本号后的Packet14c文件，或替代方案）真实排在006和007
   之间并被正确应用，历史文件未被修改（如判断必须改历史文件，本Packet不动手，
   只报告方案，不算失败）。
3. 如果本Packet找到不改历史文件即可解决007"题库已发布"阻断的方案并实现：
   `npx supabase db reset --local`完整跑通到200008，退出码0，账本正确登记。
   如果判断必须改历史文件才能解决，如实报告为BLOCKED并给出方案供用户决策，
   不算本Packet失败。
4. 既有测试、typecheck、lint通过；`git status`范围可控。

- 采取的方案与理由；如需用户授权修改历史文件，明确列出选项和风险，不要自行执行。
