# Packet: Round3/Packet8 — 批量刷新与业务事件连接

## 背景
方案文档第17、20、22节。单学生资格计算RPC已就绪：
`public.evaluate_student_course_completion(uuid, uuid, uuid)`（仅service_role可调用，
迁移`202608200004`）。本Packet把它接入真实业务事件，并提供批量/机构手动刷新能力。

## 目标
1. 在以下事件发生后，异步或安全地触发对应学生的资格重新计算（方案17："先完成权威业务
   写入，再异步或安全刷新资格"，"业务提交不得被资格计算失败阻断"）：
   - 教材章节完成。
   - 必修作业成绩发布。
   - 章节/阶段/期中/期末成绩发布（含期中`EX-K1-MID-V1`、期末`EX-K1-FIN-V1`，
     复用Round1/2已验证的`release_learning_submission_grade`等发布路径）。
   - 补考最终成绩发布。
   找到仓库中这些事件当前的真实写入点（触发器/RPC/API路由），在其后接入资格刷新，
   不要重建这些业务写入本身。
2. 新政策发布后，生成批量刷新任务，覆盖该政策适用范围内的学生（方案17）。
3. 提供机构手动刷新入口（可以是最小化RPC，正式UI在Round4）。
4. 满足性能与幂等原则（方案17、20）：批量刷新用集合查询，不逐学生循环发请求；
   同一学生同一政策并发刷新幂等（复用Packet7已实现的证据指纹去重机制）；
   不允许每次打开页面都重算全部学生。

## 非目标
- 不创建证书相关表或颁发逻辑（Round4）。
- 不做机构/学生/老师端正式UI（Round4/5）。
- 不修改Packet7已实现的单学生计算算法本身，只负责触发和批量编排。

## 验收标准
1. 真实触发一次章节完成、一次成绩发布，验证对应学生的资格记录被自动刷新
   （用真实查询对比刷新前后的`student_course_completion_evaluations`）。
2. 验证资格刷新失败（人为制造一次异常）不会导致对应的成绩发布/业务写入被回滚——
   业务写入必须先于/独立于资格刷新完成。
3. 批量刷新：对至少3个学生的场景验证使用集合查询完成（用查询计划或日志证明不是
   逐学生循环发起独立请求）。
4. 并发测试：对同一学生同一政策同时发起两次刷新，验证不产生重复/矛盾的资格记录。
5. 新政策发布后验证批量刷新任务被正确生成并可执行完成。
6. 既有测试、typecheck、lint通过；`git status`范围可控；测试数据清理。

## 交付形式（报告）
- 改动文件列表（触发点位置、批量刷新实现、测试）。
- 每条验收标准 PASS/FAIL/BLOCKED，附真实证据。
- 验证命令、退出码。
- 已知风险、性能测算方式说明。
