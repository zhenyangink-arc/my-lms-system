链路不完整"问题。这是本轮（第一轮）最后一个任务，完成后课程巩固与管理端才算真正打通。

背景文档：docs/korean-practice-center-integration-roadmap.md 第4.8、12.1节（先读文档，不要
复述给我，直接按其中定义实现）。

已完成的前置依赖（直接复用，不要重新设计）：
- 巩固包生成/发布服务：`src/features/chapter-practice/api/management-service.ts`
  （里面已有生成草稿、创建新版本、发布前检查等函数，本任务只需要调用其中"生成草稿"和"标记
  needs_update"相关能力，不要重新实现生成逻辑）。
- 覆盖矩阵和学生端目录页面路径：
  管理端 `/[space]/dashboard/admin/apps/[appSlug]/practice-center`，
  学生端 `/[space]/apps/korean/practice/course`（具体 revalidate 路径自己去项目里确认实际路由
  文件路径）。

已冻结的决策（对照文档12.1的六个步骤）：
1. 教材章节发布时，检查其关联的 `course_chapter_id` 是否存在。
2. 检查该章节的章节测试和专项练习来源是否存在。
3. 如果该章节尚无任何 `chapter_practice_units` 记录，调用生成草稿逻辑生成一版 draft
   （不自动发布，只是让平台负责人后续能在矩阵里看到"草稿待处理"而不是"未生成"）。
4. 如果该章节已有 published 状态的 `chapter_practice_units`，且本次教材发布确实改变了来源内容
   （词汇、语法、课文等），把该 published 版本标记为 needs_update；**不允许**直接修改或覆盖已
   发布版本的内容——已发布内容本身不变，只改 status 字段。判断"是否改变来源内容"可以用简单
   策略（例如比较来源数据的更新时间戳或做浅层内容摘要对比），不需要做精确的语义 diff，但要在
   报告里说明你用的判断方式。
5. 刷新管理端巩固覆盖矩阵页面的缓存（Next.js revalidatePath 或项目里已有的等价刷新机制，去找
   教材发布现有代码已经在刷新教材/章节测试/作业/学生教材页面时用的是什么机制，保持一致）。
6. 刷新学生端课程巩固目录页面的缓存，机制同上。

必须找到教材章节发布的现有 Server Action / API（自己在项目里搜索，通常在管理端教材管理相关
目录下），在其发布成功之后追加以上第3—6步逻辑，**不要修改该 Server Action 已有的教材、章节
测试、作业、学生教材刷新行为**，只追加，不删除、不重排已有步骤，不改变其现有返回值结构（除非
你新增字段是纯追加、不破坏调用方）。

不要做的事（non-goals）：
- 不允许这次追加逻辑导致教材发布这个已有动作的事务失败或明显变慢到不可接受（如果生成巩固包
  草稿失败，应该记录/降级处理，不能让整个教材发布失败——教材发布本身比巩固包草稿生成更重要，
  说明你选择的失败处理策略）。
- 不修改数据库表结构。
- 不修改学生端页面内容展示逻辑（只是刷新缓存，不改内容）。
- 不自动把 needs_update 的版本改回 published 或自动创建新发布版本，那仍需要平台负责人手动操作。

验收标准：
- 用真实数据构造：对一个"尚无巩固包"的已发布章节触发一次教材发布（或等价的真实操作路径），
  验证该章节随后出现 draft 版本的 `chapter_practice_units`，不是自动发布。
- 用真实数据构造：对一个"已有 published 巩固包"的章节，修改其教材来源内容后再次发布，验证
  该巩固包被标记为 needs_update，且其内容字段（标题、内容块等）未被覆盖改变。

  发布相关的现有自动化测试或等价真实验证。
- 验证巩固包生成失败时（可以人为制造一个失败场景，比如临时让来源查询报错）不会导致教材发布
  本身失败。
